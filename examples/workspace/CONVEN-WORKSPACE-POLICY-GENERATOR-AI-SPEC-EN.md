# Conven Workspace Policy Generator: AI Implementation Specification

## 1. Purpose of This Document

This specification guides an AI to implement from first principles a **standalone,
organization-independent Conven workspace Policy generator**. The generator targets the
`go-zero-apollo-consul-v1` profile and must:

1. scan the current workspace and its direct child repositories in read-only mode;
2. identify local services, start commands, ports, RPC bindings, and local dependencies from
   verifiable code and configuration evidence;
3. generate a complete `version: 2` candidate manifest that Conven can parse strictly;
4. generate or maintain a Python 3 plugin executable through the Conven plugin runner;
5. fail explicitly or report unresolved items when evidence is insufficient instead of guessing
   business configuration.

This is an organization-independent functional specification. Generator code, defaults, fixtures,
and examples MUST NOT embed organization names, business service names, private domains, cluster
names, namespaces, credential paths, or fixed port tables. Workspace-specific values in the
candidate may come only from explicit input files or traceable workspace evidence.

This specification is self-contained. The implementation MUST NOT depend on an external script,
organization knowledge, hidden defaults, or a preloaded service catalog. Conformance is determined
solely by this specification's normative requirements, declared inputs, and verifiable workspace
evidence.

The terms “MUST”, “MUST NOT”, “SHOULD”, and “MAY” in this document are normative.

## 2. Artifact Boundaries

The AI implementation must distinguish between two artifacts:

- **Generator plugin**: an executable Python 3 file, for example
  `generate-workspace-policy.py`. This is what `conven plugins --run` executes.
- **Candidate manifest**: a single-document YAML file emitted after the plugin scans the workspace.
  This YAML becomes `.conven/conven.yaml` only after `conven policy --import` is run.

`conven plugins --run` does not parse, validate, or import the YAML generated by a plugin. The
plugin itself MUST ensure that its output is complete, deterministic, and compliant with this
specification.

### 2.1 Input/Output Quick Reference

| Type | Name | Required | Specification |
| --- | --- | --- | --- |
| Process input | `--workspace PATH` | Yes | Canonical workspace injected by Conven |
| File input | `.conven/catalog.yaml` | Yes | Explicit repository/RPC identity, kind, local port, and disabled-binding catalog |
| File input | `conven-generator.json` | Yes | Explicit non-sensitive profile, environment, and connection inputs |
| Read-only input | Direct child repositories | Yes | Source code, build entry point, application configuration, and environment bootstrap |
| CLI override | `--disable-bindings` | No | Completely replaces `catalog.yaml`'s `disabledRpcBindings` for this run |
| Primary output | Conven manifest v2 YAML | Yes | UTF-8, one document, strict fields, complete candidate |
| Diagnostic output | stderr | As needed | Warnings, unresolved items, and fatal errors; MUST NOT be mixed into `--stdout` YAML |
| AI implementation artifact | Executable Python 3 plugin | Yes | Installable and accepts the process inputs listed in this table |

The minimum successful runtime result is “candidate YAML generated safely.” Importing and starting
are subsequent explicit Conven operations, not implicit side effects of running the plugin.

By default, the generator only produces a candidate and MUST NOT:

- modify business repository source code or in-repository configuration;
- modify or overwrite `.conven/conven.yaml`;
- run `conven policy --import` automatically;
- access a remote configuration center, service registry, or Kubernetes;
- output, copy, or commit credentials;
- use an existing manifest as an implicit merge base.

## 3. Conven Plugin Execution Contract

### 3.1 Invocation Forms

Conven supports both an explicit name and an omitted name:

```bash
conven plugins --run NAME [plugin-args...]
```

```bash
conven plugins --run [plugin-args...]
```

Plugins are installed to `<workspace>/.conven/plugins` by default;
`plugins --install --global` installs them to `~/.conven/plugins`. The same name may exist in both
scopes. An explicit `NAME` uses the workspace plugin first and falls back to the global plugin only
when no local plugin exists, with a warning. If a local entry with the same name exists but is
damaged, execution MUST fail instead of silently falling back. When `NAME` is omitted, Conven runs
the plugin with a warning if the workspace contains exactly one valid plugin, opens its single
selector when it contains multiple plugins, or opens the selector for global candidates when no
workspace plugin exists. Even one global candidate requires selection and confirmation. An
explicitly global run uses `conven plugins --global --run NAME` and requires `NAME`. The plugin
itself MUST NOT read or depend on its installed name.

Invocation examples:

```bash
conven plugins --run generate-workspace-policy \
  --output conven-candidate.yaml

conven plugins --run --output conven-candidate.yaml
```

### 3.2 Plugin File Requirements

The plugin MUST:

- use a `.py` file extension;
- have `#!/usr/bin/env python3` as its first line, or refer to an absolute interpreter whose basename
  is `python3`;
- be a real regular file, not a symbolic link;
- be executable after installation;
- use a name that starts with an ASCII letter or digit and contains only ASCII letters, digits,
  `-`, `_`, and `.` thereafter;
- preferably use only the Python standard library so Homebrew users need no extra dependencies.

### 3.3 Child Process Inputs

Conven executes the plugin as if it had run:

```text
<selected-plugin-directory>/NAME.py \
  --workspace <canonical-workspace> \
  [plugin-args...]
```

with the following runtime environment:

- the child cwd is the canonical workspace;
- `CONVEN_WORKSPACE` is overwritten with that same canonical workspace;
- Conven overwrites any pre-existing `CONVEN_WORKSPACE` value and inherits all other environment
  variables from the parent process;
- stdin, stdout, and stderr are passed through directly;
- Conven always injects `--workspace PATH` before user arguments;
- users cannot pass `--workspace` or `--workspace=...` themselves.

Conven does not provide a network or filesystem sandbox for plugins. A plugin runs with the current
user's permissions and may see tokens, proxy variables, and cloud credentials in the parent
environment. It MUST NOT enumerate, log, exfiltrate, or write these inherited variables into the
candidate.

`plugins --run` selects the nearest `.conven` **directory** walking upward from the effective
cwd as the workspace boundary. That directory need not contain `conven.yaml` yet. The command must
be invoked from inside that workspace, or with:

```bash
conven -C <workspace> plugins --run NAME [plugin-args...]
```

The user's global `~/.conven` is not a project workspace boundary.

Therefore, the plugin MUST accept and validate:

```text
--workspace PATH
```

The plugin MUST NOT depend on stdin, except for an interactive output-overwrite confirmation.

### 3.4 Plugin Exit Status and Output Streams

- Success: the plugin exits `0`.
- Argument errors or generation failures: the plugin exits nonzero and writes diagnostics to stderr.
- `--stdout` mode: stdout may contain only the UTF-8 candidate YAML; warnings and errors MUST go to
  stderr.
- File-output mode: stdout may contain a short success summary; YAML is written to the target file.
- Conven wraps any nonzero plugin exit as a `conven plugins --run` failure; the plugin MUST NOT rely
  on Conven preserving its specific nonzero exit code.
- Conven runner emits NAME-selection, scope-warning, and candidate-list output; plugin stdout must
  still obey this section.

## 4. Generator CLI Specification

The generator MUST support at least:

```text
--workspace PATH
--stdout
--check
--output [FILE]
--disable-bindings BINDING [BINDING ...]
```

### 4.1 Argument Semantics

`--workspace PATH`

- required by the plugin process interface and injected by Conven;
- may be supplied explicitly when the plugin is run directly;
- must resolve to an existing real directory;
- is the root for scanning and all default relative paths;
- its basename MUST match `[A-Za-z0-9][A-Za-z0-9._-]*`.

`--stdout`

- writes the complete candidate manifest to stdout;
- creates or overwrites no output file;
- MUST NOT be combined with `--output` or `--check`.

`--check`

- rescans the workspace and generates the result in memory;
- compares it byte-for-byte with the target file and may be combined with `--output [FILE]` to
  select that target;
- exits `0` if identical and nonzero if missing or different;
- does not modify the target file.

`--output FILE`

- selects an explicit target file;
- resolves a relative path against the workspace;
- allows an absolute path only if it also resolves inside the workspace, otherwise rejects it;
- when the target exists, may prompt for overwrite only if both stdin and stderr are interactive
  terminals;
- accepts only `y` or `yes`, ignoring case and surrounding whitespace, as confirmation;
- MUST reject overwrite in non-interactive execution and MUST NOT wait for input.

`--output` (without FILE)

- targets `<workspace>/application.yaml`.

When neither `--stdout` nor `--output` is provided:

- the default target MUST be
  `<workspace>/<workspace-name>-conven-candidate.yaml`;
- the default filename MUST NOT contain an organization name or fixed business profile name.

`--disable-bindings BINDING...`

- explicitly disables one or more RPC bindings;
- may be repeated, with the result deduplicated and stably sorted;
- when provided explicitly, completely replaces `catalog.yaml`'s `disabledRpcBindings` rather than
  appending to it;
- there MUST NOT be any binding that is hard-coded as “always disabled.”

## 5. Input Model and Evidence Priority

Inputs come from the following sources, in descending order of priority:

1. explicit CLI arguments;
2. human-declared workspace files, including `.conven/catalog.yaml` and `conven-generator.json`;
3. build, entry-point, and runtime configuration in the current workspace files, including
   uncommitted local changes;
4. inferred results that can be supported consistently by multiple independent pieces of code
   evidence.

The following MUST NOT be treated as facts:

- common-sense guesses about service names or ports;
- directory-name similarity;
- uncommitted remote service-registry state;
- the AI's prior knowledge of the business architecture;
- configuration from another workspace;
- organization-specific code constants or default tables.

When a required field cannot be proven, the generator MUST:

- report an error containing the file, field, and reason; or
- emit a warning/unresolved summary for an item that this specification explicitly permits it to
  ignore;
- never invent a value merely to produce YAML that “looks complete.”

## 6. `.conven/catalog.yaml` Input Specification

### 6.1 Location and Purpose

Fixed location:

```text
<workspace>/.conven/catalog.yaml
```

This file is the normative source for service identities, kinds, local ports, and disabled RPC
bindings. When the file is missing or invalid, generation MUST fail and print the schema plus the
discovered candidate repositories. The generator MUST NOT embed a fallback service catalog, invent
ports, or implicitly select repositories based on directory names.

An AI preparing a workspace MAY edit this file from source evidence, but MUST request input when no
unique port evidence exists. The supported Conven workflow is `conven catalog --edit`, followed by
`conven catalog --validate`. During plugin execution, the plugin only consumes the confirmed file and
does not repeat guesswork.

### 6.2 YAML Schema

The file MUST be UTF-8, contain exactly one YAML document, reject unknown fields, and use this
shape. Examples illustrate syntax only and are not default services:

```yaml
version: 1
services:
  - repository: catalog-api
    kind: http
    port: 18080
  - rpcBinding: catalogRpc
    kind: rpc
    port: 18081
  - repository: inventory-rpc
    rpcBinding: inventoryRpc
    kind: rpc
    port: 18082
disabledRpcBindings:
  - searchRpc
```

`version` MUST equal `1`. `services` is an ordered sequence. Every service MUST declare
`repository`, `rpcBinding`, or both; neither identity is implicitly synthesized. `kind` and `port`
are required. `disabledRpcBindings` is an optional ordered sequence of RPC binding names.

### 6.3 Field Constraints

Field constraints:

- `repository`: matches `[A-Za-z0-9][A-Za-z0-9._-]*`;
- `kind`: the `go-zero-apollo-consul-v1` profile permits only `http` or `rpc`;
- `rpcBinding`: starts with an ASCII letter or `_`, followed only by ASCII letters, digits, `_`, or
  `-`;
- a service with `rpcBinding` MUST use `kind: rpc`;
- `port`: a decimal integer in the range `1..65535`.

The complete catalog MUST be validated before filtering it to workspace repositories:

- repositories are unique;
- bindings are unique;
- ports are globally unique;
- format, kind, and character sets are valid.

Declaration order is the stable output order.

### 6.4 Workspace Subset Rules

- Scan only direct child directories of the workspace; do not recursively search for repositories.
- If an explicitly declared repository path does not exist, ignore it so one master catalog can
  cover different checkout subsets.
- If an explicitly declared repository path exists but its structure is incomplete, report an
  error; do not pretend that the repository was not checked out.
- Repositories present in the workspace but absent from the catalog are ignored by default.
- If no service can ultimately be generated, report an error.

## 7. Disabled RPC Binding Rules

The catalog's `disabledRpcBindings` sequence is the persisted disabled set. Every item uses the
same binding character constraints as `services[].rpcBinding` and MUST be unique. An absent or empty
sequence means the disabled set is empty. `--disable-bindings` replaces this sequence in memory for
one generator run and does not edit the catalog.

Processing rules:

- a catalog binding not declared in the final service code is ignored with a warning;
- a CLI binding not declared in the final service code is an error;
- each matched binding produces a service-level config patch for every local service that declares
  it;
- a disabled binding takes precedence over local-dependency inference;
- even if a disabled binding points to a provider in the current checkout, no corresponding local
  dependency is generated;
- all bindings use the same rules; no name-specific branch may exist.

The semantic form of a disable patch is:

```yaml
config:
  patches:
    - path: <binding>
      value:
        discovType: ""
```

This patch belongs only to the profile defined in Section 9; `discovType` is not a universal field
for arbitrary frameworks. If the source cannot prove that the client binding uses this field to
disable discovery, the entire repository MUST be treated as unsupported. The generator MUST NOT
substitute another field and continue to claim compliance with that profile.

## 8. `conven-generator.json` Input Specification

Fixed location:

```text
<workspace>/conven-generator.json
```

This file externalizes environment and connection information that cannot be inferred safely from
source. It MUST be UTF-8 JSON, MUST reject duplicate keys and unknown fields, and MUST NOT contain
tokens, certificate contents, or kubeconfig contents.

Minimum structure:

```json
{
  "version": 1,
  "profile": "go-zero-apollo-consul-v1",
  "policyName": "go-zero-apollo-consul-local",
  "environments": {
    "dev": {
      "registry": "consul",
      "connection": {
        "driver": "none"
      }
    }
  }
}
```

Example structure using ktctl:

```json
{
  "version": 1,
  "profile": "go-zero-apollo-consul-v1",
  "policyName": "go-zero-apollo-consul-local",
  "environments": {
    "integration": {
      "registry": "consul",
      "connection": {
        "driver": "ktctl",
        "namespace": "integration",
        "kubeconfigEnv": "CONVEN_KUBECONFIG",
        "sudo": true,
        "timeout": "240s",
        "args": ["--podCreationTimeout", "120"],
        "readiness": [
          {"name": "config", "address": "config.internal:8080"}
        ]
      }
    }
  }
}
```

Field rules:

- `version`: MUST be integer `1`;
- `profile`: MUST be `go-zero-apollo-consul-v1`;
- `policyName`: MUST match ASCII `[A-Za-z0-9][A-Za-z0-9._-]*`;
- `environments`: at least one environment; each key MUST match ASCII
  `[A-Za-z0-9][A-Za-z0-9._-]*` and MUST NOT be `.` or `..`; path separators, whitespace, and
  other characters MUST be rejected because the key enters a `config-<env>.yaml` filename;
- `registry`: MUST be `consul` for this profile;
- `connection.driver`: permits only `none` or `ktctl`; `command` and any other driver
  MUST NOT be emitted;
- `ktctl` may declare `args`, `kubeconfigEnv`, `context`, `namespace`, `sudo`, `timeout`, and
  `readiness`;
- every item in `args` MUST be a non-empty string; `context` and `namespace` MUST be non-empty
  strings without control characters; `kubeconfigEnv` MUST match the ASCII environment-variable
  name `[A-Za-z_][A-Za-z0-9_]*`; `sudo` MUST be boolean; `timeout` MUST be a positive Go duration
  string;
- each `readiness` item MUST have a unique `name` and a `host:port` `address`; `name` MUST match
  ASCII `[A-Za-z0-9][A-Za-z0-9._-]*`;
- final readiness for `ktctl` MUST be non-empty and may be formed by merging and deduplicating this
  file's values with validated Apollo bootstrap endpoints;
- `none` MUST NOT carry ktctl-specific fields;
- `kubeconfigEnv` stores only an environment-variable name; this file MUST NOT store a kubeconfig
  path or contents.

All JSON strings copied into the manifest MUST be emitted through a deterministic YAML-safe encoder,
not by unescaped string concatenation. The encoder MUST preserve string types and forbid tags,
anchors, and aliases; values such as `true`, `null`, `#value`, or strings containing `: ` must not
be parsed as another YAML type. The `go-zero-apollo-consul-v1` profile does not permit Conven
templates in JSON connection fields, so literal `${` in `args`, `context`, `namespace`, or readiness
`address` MUST be rejected rather than deferred to the plan stage as an unknown variable.

Every active service MUST have a bootstrap for every declared environment. Extra `config-*.yaml`
files in a repository do not create environments automatically; add an environment to this file
before using it. Thus environment, namespace, and connection mode always remain explicit inputs and
are never guessed by the generator.

If there is no environment named `dev`, later `doctor` and `services --start` commands MUST pass
`--env NAME` explicitly because Conven selects `dev` by default.

## 9. Supported Typed Profile

### 9.1 Support Boundary

This specification defines the following typed profile for local registration isolation and
routing:

```text
language/build: Go
framework: go-zero
config source: Apollo
discovery: Consul
materializer: yaml-overlay
service kinds: http, rpc
```

This support boundary comes from Conven's runtime isolation contract, not from an organizational
rule.

This specification does not define runner-only services, mixed technology stacks, or other
configuration sources. If another language, framework, materializer, discovery mechanism, or server
kind is found, the generator MUST mark it unsupported and stop generation. It MUST NOT fabricate a
`go-zero` policy or typed isolation for that service. Other technology combinations are outside the
scope of this profile.

### 9.2 Go Repository Layout Contract

An explicitly declared service repository governed by this profile MUST contain:

```text
<repository>/.git             # Git metadata entry; file or directory
<repository>/go/go.mod
<repository>/go/main.go
<repository>/resources/application.yaml
<repository>/resources/config-<env>.yaml
```

This layout is not a global Conven rule, but it is the fixed input contract for this profile. A
layout that does not conform MUST be treated as unsupported and fail; multiple layouts MUST NOT be
mixed silently within one profile.

Validation rules for the Go adapter defined by this profile:

- the module basename in `go.mod` equals the repository directory name;
- `main.go` is `package main`;
- the entry point declares a configuration-directory argument and completes flag parsing before
  initializing remote configuration;
- scan non-test `.go` files under `go/`, excluding hidden paths;
- exactly one server kind must be proven:
  - `zrpc.RpcServerConf` => `rpc`;
  - `rest.RestConf` => `http`;
- the detected result MUST match the catalog kind;
- an RPC client binding comes from the YAML field tag of `zrpc.RpcClientConf`;
- an RPC provider key comes from root-level `consul.key` in the application;
- a client target key comes from `<binding>.consul.key`;
- an RPC application's root MUST contain scalar `discovType` and `listenOn` values;
- an HTTP application's root MUST contain scalar `host` and `port`; if the root contains
  `discovType`, it too MUST be scalar and MUST NOT have the value `consul`. The adapter defined by
  this profile treats HTTP registration as `not-applicable` and does not disable Consul
  registration for HTTP services.

The implementation MUST identify server kinds and YAML field tags from Go syntax and MUST NOT treat
comments or string literals as evidence. It MAY use the Go parser or another analysis method that
provides equivalent guarantees. Conflicting server-kind evidence or an inability to determine the
kind uniquely MUST fail generation. Any helper analysis tool MUST be invoked through argv rather
than a shell and MUST NOT modify the repository as a side effect.

## 10. Environment and Configuration Discovery

### 10.1 Environment Set

The generator MUST NOT hard-code `dev`, `test`, or any other environment name. The output
environment set is exactly the key set of
`conven-generator.json.environments`. Every active service MUST contain a corresponding
`config-<env>.yaml` for every environment; any missing file is an error. The plugin does not obtain
temporary environment additions from stdin.

### 10.2 Apollo Bootstrap Evidence

For each environment, the bootstrap must prove at least:

- `appId` is non-empty;
- `cluster` is non-empty;
- `ip` is either `host:port` or `http(s)://host:port` without path, query, or userinfo;
- `namespaceName` is exactly `application.yml`. This is a technical contract of the
  `go-zero-apollo-consul-v1` profile. A different Apollo namespace is outside this profile and MUST
  be rejected rather than guessed or silently accepted.

Multiple distinct Apollo endpoints for the same environment and cluster are an error.

### 10.3 Connection and Readiness

The following values MUST NOT be hard-coded:

- connection driver;
- Kubernetes context;
- namespace;
- kubeconfig file;
- Consul or Apollo domain;
- readiness endpoint.

Connection configuration comes exactly from `conven-generator.json`, and only `none` or `ktctl` is
allowed. With `ktctl`, final readiness MUST contain at least one item. Explicit readiness values are
merged with bootstrap endpoints; a name conflict with different addresses is an error. Kubeconfig
is referenced only through `kubeconfigEnv`; credential contents MUST NOT be written into the
manifest. Any other driver MUST be marked unsupported even if it appears in code.

## 11. Binding-Only Provider Inference

For `binding:<rpc-binding>,rpc,port`:

1. find `<binding>.consul.key` in the current active consumer services;
2. if no key evidence exists, keep the entry unresolved and ultimately ignore it;
3. if multiple distinct target keys exist, report an ambiguity error;
4. match the unique target key against root `consul.key` values of candidate RPC repositories in
   the workspace;
5. if no provider exists, keep the entry unresolved and ultimately ignore it;
6. if multiple providers match, report an ambiguity error;
7. for a unique provider, scan it strictly with the full repository adapter;
8. after adding a provider, reprocess other unresolved bindings to allow chained discovery;
9. if a binding resolves to a repository that is already configured explicitly, report an error
   and require consolidation into one entry that declares both `repository` and `rpcBinding`.

For `repository,<binding>,rpc,port`:

- strictly scan the repository when it exists;
- when consumer binding target-key evidence exists, it MUST equal the provider's root `consul.key`;
- multiple distinct target keys are an ambiguity error;
- when no consumer evidence exists, the explicit repository declaration MAY remain, but the report
  SHOULD mark the alias as unverified.

## 12. Local Dependency Inference

Dependencies are inferred only among final active services.

Algorithm:

1. build a `root consul.key -> service name` mapping for every active RPC provider;
2. provider keys MUST be unique among active services;
3. for every client binding of every consumer, read its target `consul.key`;
4. when the target key equals an active provider key, generate a local dependency;
5. when the target does not belong to an active provider, generate no dependency and preserve the
   original configuration for remote routing;
6. ignore self-dependencies;
7. if multiple bindings of one consumer point to the same local provider, report an error and
   require explicit disambiguation;
8. exclude disabled bindings before Step 3.

Dependency output:

```yaml
dependencies:
  <provider-service>:
    localService: <provider-service>
    binding: <consumer-binding>
    port: rpc
```

`localService` MUST be a service present in the candidate manifest, and `port` MUST refer to a
declared port name on that service. Every generated environment MUST also emit an explicit
`mode: remote` resolution for the owner/alias; selecting the provider service locally overrides it
with local resolution.

## 13. Conven Manifest Output Specification

### 13.1 Basic YAML Constraints

The output MUST:

- be UTF-8;
- be a single YAML document;
- end with a newline;
- contain only `version`, `workspace`, `environments`, `policies`, and `services` at the top level;
- contain no unknown fields;
- use exactly integer `2` for `version`;
- have a non-empty `workspace.name`;
- contain at least one service;
- use no YAML merge keys, implicit business defaults, or multi-document separators;
- produce byte-for-byte stable output for identical input.

Service, policy, and environment names MUST match ASCII
`[A-Za-z0-9][A-Za-z0-9._-]*`; environment names also MUST NOT be `.` or `..`. A binding MUST match
ASCII `[A-Za-z_][A-Za-z0-9_-]*`. Kind and port names MUST be non-empty and contain no Unicode
whitespace; kind and port names generated by the `go-zero-apollo-consul-v1` profile must additionally
use the fixed enumerations defined in this document.

### 13.2 Top-Level Structure

Logical structure:

```yaml
version: 2

workspace:
  name: <workspace-name>
  policy: <default-policy-name>

environments:
  <environment-name>:
    registry: <registry-name>
    # connection only when proven or explicitly configured

policies:
  <default-policy-name>:
    drivers: {}
    config: {}
    process: {}
    routing: {}

services:
  <service-name>: {}
```

When present, `workspace.policy` MUST refer to an actual key in `policies`. A service may override
the workspace default through `service.policy`, but that reference MUST also exist.

### 13.3 `go-zero-apollo-consul-v1` Typed Policy

Only when source evidence satisfies the profile in Section 9 may the generator emit a policy with
the following semantics. The actual policy key comes from `conven-generator.json.policyName`; the
name below is only an organization-independent example:

```yaml
policies:
  go-zero-consul-local:
    drivers:
      framework: go-zero
      configSource: apollo
      discovery: consul
      materializer: yaml-overlay
    config:
      sourceDir: resources
      application: application.yaml
      bootstrap: config-${env}.yaml
      runtimeBootstrap: config-local.yaml
      apollo:
        attempts: 5
        retryDelay: 2s
        timeout: 15s
      patches:
        - file: config-local.yaml
          path: localConfigEnable
          value: true
        - file: config-local.yaml
          path: localConfigPath
          value: ${configDir}/application.yaml
    process:
      env:
        PROFILE_ACTIVE: local
      args: [-f, "${configDir}"]
    routing:
      servers:
        rpc:
          port: rpc
          isolation:
            registration:
              mode: config
              path: discovType
              disabledValue: ""
            listener:
              path: listenOn
              value: "127.0.0.1:${port.rpc}"
        http:
          port: http
          patches:
            - path: port
              value: "${port.http}"
          isolation:
            registration:
              mode: not-applicable
            listener:
              path: host
              value: "127.0.0.1"
      localDependency:
        mode: replace
        value:
          target: "127.0.0.1:${dependency.port}"
      remoteDependency:
        mode: preserve
```

This is the exact contract of the `go-zero-apollo-consul-v1` profile, not a universal convention for
all go-zero projects. Before generation, the implementation MUST validate that the target project
actually uses the paths and semantics `resources`, `config-local.yaml`, `-f`,
`PROFILE_ACTIVE=local`, `localConfigEnable`, `localConfigPath`, `discovType`, `listenOn`, `host`, and
`port`. If any item is not valid, the repository MUST be unsupported and generation MUST fail. The
generator MUST NOT emit a typed policy variant that this specification does not define and claim
that it conforms to this profile.

### 13.4 Service Output

Service shape for the Go adapter defined by this profile:

```yaml
services:
  <service-name>:
    path: <repository-relative-path>
    kind: <http-or-rpc>
    runner:
      workdir: go
      build: [go, build, -o, "${artifact}", .]
      run: ["${artifact}"]
    ports:
      <kind>: <validated-port>
    health:
      type: tcp
      address: "127.0.0.1:${port.<kind>}"
```

Requirements:

- `path` MUST be an existing workspace-relative path;
- `runner.run` is required;
- commands use argv arrays and do not go through a shell;
- every command element is non-empty;
- ports are in the range `1..65535`;
- the kind of a typed service MUST exist in the policy's routing servers;
- the service port corresponding to that kind MUST exist;
- the health address MUST use loopback and the service's declared port.

### 13.5 Template Variables

Conven manifest v2 supports only the following variables:

```text
${workspace}
${service}
${serviceDir}
${stateDir}
${runDir}
${configDir}
${artifact}
${env}
${port.NAME}
${services.NAME.ports.PORT}
${dependency.name}
${dependency.port}
```

The final two variables are used only in a dependency route value. Do not invent new template
variables or assume that all YAML fields are interpolated automatically.

## 14. Static Invariants and Runtime Assumptions

“The YAML can be imported” does not mean “the service can be started.” The generator MUST check the
following static invariants offline:

- service path and runner workdir actually exist;
- runner run has complete executable semantics;
- policy `sourceDir` is a relative subdirectory that is neither `.` nor `..` and cannot escape;
- policy `application` is a relative file that is not `.` and cannot escape;
- `yaml-overlay` is paired with `configSource: apollo`;
- an Apollo source declares both bootstrap and runtimeBootstrap;
- every patch path is a non-empty dot-separated path and its value is non-null;
- route mode uses only `preserve` or `replace`;
- a replace route has a value;
- RPC registration isolation uses config mode;
- the RPC listener is `127.0.0.1:<declared-rpc-port>`;
- HTTP registration isolation is `not-applicable`;
- the HTTP listener host is a loopback IP without a port;
- a typed go-zero process appends exactly one `-f <absolute-runtime-config-dir>`;
- runtime bootstrap is exactly `config-local.yaml`, and final `PROFILE_ACTIVE` is exactly `local`;
- a local dependency has either a policy local route or explicit localEnv;
- an unselected dependency preserves remote configuration through an explicit environment `mode: remote` resolution;
- no dependency points to a service outside the manifest;
- no self-dependency is generated.

The following are runtime assumptions that an offline plugin cannot prove. They MUST appear in the
success report, and the generator MUST NOT claim to have validated them:

- the Apollo endpoint is reachable on the actual network and permits the Apollo adapter defined by
  this profile to make an unauthenticated `GET /configs/...` request; this profile has no Apollo
  credential/header input fields;
- the final application returned by Apollo is consistent with repository evidence;
- the final application root still contains scalar RPC `discovType`/`listenOn` or HTTP `host`;
  HTTP root `discovType` MUST NOT be `consul`;
- ktctl, the Kubernetes context, namespace, and readiness are valid on the target machine;
- each Consul dependency not started locally has a passing instance;
- build, process, health check, and actual port listening succeed.

Acceptance results MUST be classified by level:

- **A / import-valid**: the YAML passes Conven's strict schema;
- **B / plan-valid(environment, service-selection)**: for a specified environment and local-service
  set, both `doctor` and `services --start --dry-run` pass the local static plan. Passing once does
  not cover another environment or service combination; the report MUST list the tuples actually
  validated. The entire candidate may be called plan-valid only if all declared environments and
  the promised service-selection matrix pass;
- **C / start-validated**: real materialization, connection, build, start, health, and remote
  dependency preflight all pass. Level C requires explicit user authorization and network access;
  the generator MUST NOT run it by default or report it as completed.

## 15. Determinism and Safe Writes

### 15.1 Stable Ordering

- services follow declaration order in `.conven/catalog.yaml`;
- inferred services follow the order of the binding entries that triggered them;
- disabled bindings are sorted by name;
- dependency targets follow final service order;
- environments and readiness use stable sorting;
- map output order MUST be controlled explicitly and MUST NOT depend on unstable iteration.

### 15.2 Write Protocol

- complete all scanning and validation before writing begins;
- create a temporary file in the target directory;
- write, flush, fsync, and then publish atomically;
- use no-clobber for a new file;
- overwrite only through atomic replace after interactive confirmation;
- output files SHOULD use mode `0644`;
- on failure, remove the temporary file and leave the original target unchanged.

### 15.3 Path Safety

- canonicalize the workspace; the realpath of every service path MUST remain inside the workspace;
- service paths, read bootstrap/application files, and the config source tree MUST NOT be symlinks;
- any symlink inside the config source tree is an error; the `.git` metadata entry is exempt;
- the canonical path of an explicit output MUST remain inside the workspace and MUST NOT point to a
  symlink;
- do not scan paths outside the workspace;
- do not execute shell strings assembled from repository content;
- do not print complete environment variables, tokens, kubeconfig contents, or remote configuration
  responses in logs.

## 16. Error and Warning Classification

The following conditions MUST fail:

- invalid workspace;
- invalid catalog YAML or schema;
- duplicate repository, binding, or port;
- explicitly present repository with an incomplete structure;
- catalog kind inconsistent with source kind;
- duplicate active RPC provider key;
- a binding matching multiple target keys or multiple providers;
- an explicit CLI disabled binding not declared in code;
- generated output cannot satisfy the Conven v1 schema;
- output exists and overwrite cannot be confirmed safely.

The following conditions MUST continue after a warning:

- a catalog repository is not checked out;
- a binding-only entry lacks consumer-key evidence;
- a binding-only entry has a unique key but no local provider;
- a binding from `disabledRpcBindings` is not declared in final active services;
- a dual-identity entry lacks consumer evidence, so its RPC alias is unverified.

These warnings MUST contain a source file and line number. They MUST NOT be silently ignored and
MUST NOT output secret values.

A stable diagnostic format is recommended:

```text
warning: <source>:<line>: <code>: <message>
generation failed: <source-or-stage>: <message>
```

Workspace/runtime diagnostics that cannot map to a source line use an explicit stage, such as
`workspace`, `discovery`, `render`, or `output`. The diagnostic format MUST NOT require callers to
parse ANSI colors.

## 17. Acceptance Workflow

### 17.1 Plugin Implementation Check

First define absolute paths and confirm that the current workspace already has a `.conven`
workspace boundary:

```bash
workspace="$(pwd -P)"
: "${PLUGIN_SOURCE:?set PLUGIN_SOURCE to the absolute generator plugin path}"
plugin_source="$PLUGIN_SOURCE"
plugin_name="$(basename "$plugin_source" .py)"
test -d "$workspace/.conven"
test "${plugin_source#/}" != "$plugin_source"
test_dir="$(mktemp -d "$workspace/.conven/generator-test.XXXXXX")"
candidate_stdout="$test_dir/from-stdout.yaml"

PYTHONPYCACHEPREFIX="$test_dir/pycache" \
  python3 -m py_compile "$plugin_source"
python3 "$plugin_source" --workspace "$workspace" --stdout \
  > "$candidate_stdout"
```

The unique test directory ensures that the shell does not truncate an existing file. Confirm that
the stdout file contains only YAML and diagnostics appear only on stderr.

### 17.2 Conven Plugin Check

```bash
candidate_named="$test_dir/from-explicit-name.yaml"

# Default installation is workspace-local and may ask before replacing a same-name copy.
conven -C "$workspace" plugins --install "$plugin_source"
conven -C "$workspace" plugins --list

conven -C "$workspace" plugins --run \
  "$plugin_name" --output "$candidate_named"

cmp "$candidate_stdout" "$candidate_named"
```

When this plugin is the workspace's only valid workspace plugin, omitted `NAME` MUST also be tested:

```bash
candidate_default="$test_dir/from-default-plugin.yaml"
conven -C "$workspace" plugins --run \
  --output "$candidate_default"
cmp "$candidate_named" "$candidate_default"
```

If the workspace has multiple plugins, perform this check in a disposable workspace fixture that
contains only this plugin. Do not delete another user plugin to satisfy the test. The semantics of
the injected `--workspace` and plugin arguments MUST be identical for explicit and omitted `NAME`.

### 17.3 Strict Manifest Validation

Do not replace the real manifest before review. Import may be validated in a disposable workspace:

```bash
validation_root="$(mktemp -d)"
mkdir -p "$validation_root/.conven"
conven -C "$validation_root" policy --import \
  "$candidate_named"
```

This proves only A / import-valid. It does not prove that service paths in the candidate can run in
the temporary workspace. The report MUST NOT upgrade this result to plan-valid or start-validated.

After a human reviews the candidate and explicitly agrees to replacement, import the actual file
generated in this run with:

```bash
conven policy --import "$candidate_named"
```

`policy --import` is complete replacement, not merge. `--edit` enters an interactive editor and may
be used only as an optional human publication step; it is not part of reproducible automated
acceptance.

Next, run the following command template separately for **every** environment declared in
`conven-generator.json` and every promised local-service set, recording the exact tuple in the
report. Do not validate one environment and claim that the entire candidate has reached Level B:

```bash
conven doctor --env ENVIRONMENT
conven services --start --env ENVIRONMENT --dry-run SERVICE...
```

### 17.4 Required Regression Scenarios

- missing catalog, invalid YAML, multiple documents, unknown fields, and an empty service list;
- missing generator JSON, unknown fields, invalid profile, and invalid connection driver;
- `.`, `..`, path separators, whitespace, or non-ASCII-safe characters in environment names;
- YAML-special values, control characters, and forbidden `${...}` in JSON connection strings;
- whitespace before a comment;
- catalog declarations exceeding checked-out repositories;
- an explicitly present but incomplete repository;
- an undeclared workspace repository;
- successful binding-only inference;
- missing key, missing provider, multiple keys, and multiple providers;
- matching, mismatching, and unproven dual-identity entries;
- HTTP root `discovType: consul` MUST be rejected;
- empty, invalid, and duplicate entries in `disabledRpcBindings`;
- CLI disabled entries completely replace the catalog sequence in memory;
- a disabled binding that points to an active provider still creates no local dependency;
- `--stdout`, `--check`, new-file output, interactive overwrite, and non-interactive overwrite
  rejection;
- output YAML is one document, has no unknown fields, and can be imported by Conven;
- identical inputs produce byte-for-byte identical output on repeated runs.

## 18. Prohibited AI Behavior

The AI MUST NOT:

- embed real service names or business binding names;
- embed an organization-specific policy name;
- hard-code `dev/test`, namespace, cluster, Consul/Apollo address, or kubeconfig;
- guess a port, dependency, service kind, or run command;
- treat every Go repository as a go-zero service;
- disguise an arbitrary framework as the `go-zero-apollo-consul-v1` typed profile;
- generate a dependency pointing to a nonexistent service or port merely to satisfy the schema;
- modify a business `application.yaml` automatically;
- import the candidate automatically;
- leave a partially written file after failure;
- mix warnings into `--stdout` YAML;
- read stdin in a way that blocks non-interactive execution;
- access the network to fill in information that cannot be proven from the workspace.

## 20. Definition of Done

Completion requires all of the following:

- `conven plugins --install` accepts the plugin;
- an explicit `NAME` invocation runs successfully;
- plugin logic does not depend on its own `NAME`, and an omitted `NAME` invocation also succeeds
  when it is the only workspace plugin;
- Conven v1 parses the candidate strictly;
- every workspace-specific value in the candidate is traceable to explicit input or validated
  workspace evidence;
- every service, port, runner, binding, dependency, environment, and connection has workspace
  evidence or explicit input;
- disabled-binding semantics are consistent in both patches and dependencies;
- output is deterministic, reproducible, and written safely;
- no existing file is overwritten and no real manifest is imported without user confirmation;
- acceptance tests and unresolved reporting are complete.
